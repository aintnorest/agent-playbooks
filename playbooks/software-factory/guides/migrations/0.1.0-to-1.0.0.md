# Migrate consumer repositories from 0.1.0 to 1.0.0

## Breaking changes

- The `approved:` frontmatter key is removed from product documents. Developer approvals live in `docs/user-approvals.json`, a JSON object mapping repository-relative forward-slash paths to 64-lowercase-hex body hashes. Agent acceptances live in `docs/agent-approvals.json`, a JSON object mapping paths to exactly `{ "hash": "<64 lowercase hex>", "evidence": "<non-empty text>" }`. `state` and document `revision` remain in frontmatter; approval records contain no metadata beyond hash and agent evidence.
- The developer owns and edits the user file by hand. Its existence opts the repository into factory enforcement; `{}` is valid. No agent, tool, or script writes this file. The agent file may be missing until the first acceptance and is written only through `doc_approval`.
- `check_doc_status` JSON metadata changes to `{path, type, state, revision, approval: {gate, valid}}`. Update callers of the former frontmatter approval field to read the derived `approval` object instead.
- Technical designs (TDDs) and implementation plans are agent-gated, not developer-gated. Product vision, architecture, PRDs, and system designs remain developer-gated. The roadmap is ungated and may not have an approval entry.
- `doc_approval` exposes only `status`, `accept`, and `revoke`. Accept and revoke apply only to agent-gated documents; normal acceptance takes no evidence argument and requires a review ledger closed on the current body hash. `/playbook-hash <path>` is read-only and displays a paste-ready entry for the developer.
- Body changes automatically lapse approval. Lifecycle-only frontmatter changes do not; approval validity compares only the current body hash with the appropriate file's entry.
- The implementation orchestrator reports decisions, blockers, and completion to its caller rather than asking the developer directly. Callers present developer requests and obtain validation themselves.

The [document contracts](../product-documentation-process.md#document-contracts) own document formats, [approvals](../product-documentation-process.md#approvals) own validity and authority, and [implementation execution](../product-documentation-process.md#implementation-execution) owns caller responsibilities.

## Before you start

Use the 1.0.0 tools and preserve an inventory of legacy `approved:` dates until migration is complete. A legacy date is migration evidence, not permission for an agent to record developer approval. Preserve document bodies, lifecycle states, and revisions unless the developer requests a separate change.

In the CLI fallbacks below, replace `<playbook>` with the path to the Playbook install or checkout, and run the commands from the consumer repository root.

## Migration steps

1. **Inventory legacy keys.** Inspect product vision, architecture, roadmap, PRDs, system designs, TDDs, and implementation plans. Distinguish `approved:` frontmatter keys from examples in bodies. Retain each path, type, state, revision when present, and legacy date.

2. **Ask the developer to create the user file.** The developer creates `docs/user-approvals.json` by hand as `{}` if it does not exist; preserve existing entries. Its existence enables factory enforcement, so missing approvals and legacy frontmatter may block ordinary factory work until migration finishes.

3. **Obtain developer approvals.** For every developer-gated document in `active` or `done`, render a [gate request](../communication-policy.md#gate-requests) naming its current content and legacy date when available. Keep the per-type acceptance meaning: product vision and PRDs require reading in full and accepting their content; architecture and system designs require understanding and agreeing with their technical decisions well enough to explain and defend them. Ask the developer to run:

   ```text
   /playbook-hash <path>
   ```

   The command shows the path and a paste-ready `"<path>": "<hash>",` entry. The developer pastes that line into `docs/user-approvals.json` after accepting the document, maintaining valid JSON (omit a trailing comma on the final entry). Agents never paste it on the developer's behalf. A legacy date alone does not approve the current body. If approval is withheld or changes are requested, leave the gate unresolved and follow the normal review and gate procedures. Draft and superseded documents do not need approval to remain in those states.

4. **Re-accept agent-gated documents.** For every `active` or `done` TDD and implementation plan with a legacy date, use the CLI-only migration option `--migrated-from <date>`, substituting the inventoried date. This migration path records generated migration evidence without requiring a ledger and is not exposed through `doc_approval`:

   ```sh
   python3 <playbook>/scripts/doc-approval.py --accept --repo . \
     --path docs/features/example/tdd.md \
     --migrated-from 2026-09-30
   ```

   This creates or updates only `docs/agent-approvals.json`. Without a legacy approval, use the [review loop](../document-review.md#review-loop) and normal checks before acceptance; do not invent migration evidence. Draft or superseded documents need no acceptance. Never use agent acceptance for a developer-gated document.

5. **Remove legacy frontmatter keys.** Remove `approved:` from every inventoried product document, including drafts and superseded documents. Discard roadmap dates without creating any entry. Preserve the other frontmatter and body. Removing the key before recording approvals is also safe if the inventory is retained: hashes cover only bytes after frontmatter. For plans, plain `- Assigned worktree:` and `- Assigned branch:` lines are excluded from the hash. All other body changes lapse approval; do not change bodies between approval and the final check.

6. **Check every migrated document.** Run `check_doc_status` mode `check` for each migrated path. The CLI fallback from the consumer root is:

   ```sh
   python3 <playbook>/scripts/check-doc-status.py --check <path...>
   ```

   Use mode `json` to inspect the new metadata shape when updating callers. Resolve legacy-key, malformed-file, missing-approval, and hash-mismatch diagnostics through the appropriate review or approval procedure. Do not change lifecycle states merely to silence diagnostics.

Migration is complete when all legacy keys are removed, every active or done gated document has a current matching hash in its gate's file, and every migrated document passes `check_doc_status`. Keep both files with the governing documents, and resume factory work only after unresolved developer gates have been approved.
