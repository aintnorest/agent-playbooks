# Skill construction contract

## Scope and disclosure

A Software Factory skill is the generated task an agent autoloads, hidden from the global skill menu. Disclosure has three tiers: the [agent description](agents.md#description-contract) routes the request, `SKILL.md` supplies always-needed instructions, and `references/` supplies conditional guidance. [Routing cases](agents.md#routing-cases) and the [skill source sections](skill-authoring.md#design-the-common-task-contract) have separate owners.

The publisher owns `skills/<name>/`; authors edit `skill-sources/` and `guides/`, never generated files. The directory is not named `prompts/` because OMP discovers an extension package's `prompts/` as slash prompt templates; if the package ever ships prompt templates deliberately, they go there and skill sources stay here. A task links each reference from Instructions or Output at the point of need and states when to read it through `skill://<name>/references/<file>`. Reference files are one level deep, not independently discoverable as skills. The agent must read one when its condition holds.

## Classify guidance

Required guidance is inlined only when it applies on every run. Move conditional blocks to references: a phase reached only after prerequisites pass, a language or mechanism that may be absent, a repair or follow-up loop, an exceptional mode, and OMP-specific ask mechanics are not always-needed guidance. Link the reference from the step that triggers it, state the condition, and require reading it before acting; a reference manifest entry alone is not a trigger. Select the smallest authoritative section; do not overlap selected ranges across manifests or leave a second copy inline. Communication rules are reference guidance for every task, read before any message, report, or question to the developer.

The owning document contract stays inline for drafts and reviews of that type. Independent-review context, evidence and authority, and findings stay inline for document reviews; code-review guidance for code reviews; the respective drafting or review contract for skill tasks; and the already-selected technical-writing sections for system-architecture, system-design, and technical-design drafts. Normally reference decisions, roadmap, requirement identifiers, minor changes, reference-over-repetition, feature slices, behavioral acceptance, technical contracts and verification, and reference rules. System-architecture, system-design, and technical-design reviews reference the whole technical-writing guide.
Focused code reviews inline their standard's scope and core standard alongside the shared code-review contract; their language considerations remain conditional references read when that language is present.

Fixed exceptions: draft-technical-design and review-doc-technical-design inline behavioral acceptance and technical contracts and verification; review-doc-coherence inlines governing principles, documentation hierarchy, and reference-over-repetition, and reads each represented document role's contract as a mandatory conditional reference because it reviews a variable set rather than one document type; review-doc-prd inlines requirement identifiers. Draft-prd keeps requirement identifiers as a reference, read once requirements are stable. Report any proposed additional exception and retain the default.

## Budget and description

`SKILL.md` must not exceed 500 lines or 3,800 words (about 5,000 tokens); the publisher rejects oversize output and warns at 90% of either limit (450 lines or 3,420 words). Words are a dependency-free token proxy, uncertain by roughly 20%. Before expanding a near-budget skill or resolving a warning, follow [near-budget skills](#near-budget-skills). Keep the skill procedural, not a fact store.

The skill frontmatter description is the first paragraph of the skill source's Purpose, joined on one line, 1–1,024 characters. It describes the task, not its dispatch; agent description rules live in the [agent guide](agents.md#description-contract).

## Near-budget skills

The budget is a maintenance signal, not a measured quality limit: no cited source places a degradation threshold near 5,000 tokens, and the cited evidence ties degraded adherence to the number of rules active at once and to irrelevant text, not to file length itself. A warning requires a decision, not necessarily a shorter or split skill. Decide in this order, and state the chosen step and its reason in the change that resolves the warning; a draft that adds text to a near-budget skill takes the same steps first.

1. **Measure where the words are.** Count the words the skill source contributes and the words each inlined guide section contributes. Shared contracts that every skill in a family inlines, such as review report delivery, document-review authority and findings, or the code-review contract, travel with any agent doing that kind of work; splitting the task does not shrink them.
2. **Remove what is not needed on every run (default).** Move conditional blocks to references under [classify guidance](#classify-guidance), and delete restatements and explanation that change no behavior. Never defer an unconditional rule or an owning contract required by the exceptions above, and never compress a needed rule into a slogan: guidance collapsed too far can perform worse than none. Cut item by item rather than rewriting the body; keep each rule next to the example that defines what it matches, keep its position when position carries its priority, and check the agent against known runs afterward.
3. **Split into separate agents only when the work itself separates.** All of these must hold: each half answers a self-contained question from evidence it can gather alone; most rules in one half do not apply to the other half's work; both halves report in one findings format and severity vocabulary; and a named caller merges their results, removes duplicates, resolves disagreements, and owns every check that needs both halves. Do not split when findings depend on reasoning across both halves, such as consistency or ownership between document sections, traceability from design to plan, or behavior to tests; when both agents would read nearly the same material; or when the boundary is chosen to fit the budget. A split copies every inlined shared contract into both skills, adds a dispatch and merge to every run, and introduces handoff failures; each new agent also needs its own description and routing cases under the [agent guide](agents.md).
4. **Do not give one agent a second skill to pass the budget.** An autoloaded skill loads on every run, so a second one gives the agent the same instructions plus another wrapper; the build check requires `autoloadSkills` to name exactly one skill. Reuse across tasks belongs in a shared guide section, and text needed only sometimes belongs in a reference.
5. **Raise the budget when what remains is needed on every run.** If steps 2 and 3 leave only unconditional rules and owning contracts, propose a higher limit in `scripts/build-skills.py` and this guide rather than deleting needed rules or deferring them to a reference the agent may skip. Support the proposal with real runs: compare the current and candidate skills on the same inputs and report missed findings, false findings, and token cost.

A skill review applies the same order. Being near budget is not a defect by itself; a finding names the step that applies and the evidence for it, and a proposed split that fails any step-3 condition is not a supported correction.

## Failure-driven maintenance

An optional `Gotchas` section in a skill source records observed failures. Use bullets of the form `- **<failure in ≤8 words>** — <rule>. Evidence: <record id or date>.` Never emit an empty section. Keep entries append-mostly; cross-task rules belong in their shared guide.

The loop is evidence-driven: run the agent on real work, dispatch `review-friction` for that agent over a time window to collect evidence records from its runs ([friction review](friction.md)), then dispatch `review-skill` with the skill source, generated skill, intended contract, and the friction findings as its evidence records. The caller that started the loop reads the skill review, decides which corrections to make, and applies them in a writable Playbook checkout; nothing is filed elsewhere. An evidence record is a pointer plus a judgment: the path and line range of the run's session transcript (`<session>/<AgentId>.jsonl`, whose `session_init` entry carries the exact system prompt, task, tools, and model that ran) or an `omp --export` of it, the playbook commit the skill was built from (or, when that is unknown, the latest commit before the run), and the observed result. Do not paraphrase the skill revision; the transcript is the revision. Trace each finding to its editable owner: a task-specific procedural failure becomes a Gotchas entry, dispatch ambiguity tightens the agent description, and a mistaken activation boundary changes a routing case. Regenerate and inspect the affected skill, not its compiled copy. Check other consumers before changing shared guidance. Moved rules can change salience, and conditional reads may still be missed despite checked links; both are things to watch for in evidence records.

Bundled scripts are not used because read-only review agents cannot run `bash`.

## Evidence and limits

- Anthropic's [overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) describes progressive disclosure; it specifies a platform rather than this playbook. Its [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) favor compact bodies and shallow references; guidance is not a measured result here. The [agentskills.io specification](https://agentskills.io/specification) sets a portable format; portability does not ensure correct dispatch. Neither source derives its 500-line or 5,000-token recommendation from an experiment. [Perplexity](https://www.perplexity.ai/hub/blog/designing-refining-and-maintaining-agent-skills-at-perplexity) describes skill maintenance and tested descriptions; its operational results are not our routing evidence.
- [SkillsBench](https://arxiv.org/abs/2602.12670) favors focused skills; its benchmark tasks do not measure every playbook workflow, and its comparisons by skill count and size stratify different tasks rather than splitting the same content. [Procedural-anchor and routing research](https://arxiv.org/abs/2608.14036) favors procedures over fact stores and warns about larger pools; its routing is not OMP dispatch. [Skill-defect research](https://arxiv.org/abs/2608.08453) identifies metadata, size, and resource problems; prevalence is not a local defect count.
- [Context Rot](https://trychroma.com/research/context-rot) shows distraction from excess context; its tasks do not make every detail harmful. [GSM-IC](https://arxiv.org/abs/2302.00093) tests irrelevant on-topic text; its arithmetic tasks are not playbook work. [ACE](https://arxiv.org/abs/2510.04618) supports itemized relevant detail and shows a context collapsed from 18,282 to 122 tokens scoring below its baseline; its results do not require unconditional loading. [On-demand-read research](https://arxiv.org/abs/2602.05447) reports gains for frontier models and losses for open-source models; gains do not ensure every read occurs.
- [Curse of Instructions](https://shivam.dev/papers/curse-of-instructions.pdf), its [ManyIFEval follow-up](https://aclanthology.org/2025.findings-emnlp.896/), and [IFScale](https://arxiv.org/abs/2507.11538) show that satisfying every instruction becomes less likely as simultaneous instructions grow; their simple output constraints set no token threshold for review contracts, and strong reasoning models held near-perfect adherence through roughly 100 to 250 keyword instructions.
- [Scaling agent systems](https://arxiv.org/abs/2512.08296) found multi-agent designs gaining substantially on parallelizable tasks and losing 39–70% on sequential ones at controlled budgets; none of its tasks is a review. [MAST](https://arxiv.org/abs/2503.13657) catalogs handoff, withheld-information, and verification failures in multi-agent systems; a failure taxonomy is not a rate for two read-only reviewers. Cognition's [argument against multi-agents](https://cognition.com/blog/dont-build-multi-agents) for interdependent work is practitioner opinion.
- Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) gained on breadth-first research at a large token cost and found one judge applying a full rubric more consistent with humans than separate judges per criterion; it reports no sample sizes. [TICK](https://arxiv.org/abs/2410.03608) and [CheckEval](https://arxiv.org/abs/2403.18771) improve or match evaluation by answering checklist items individually; they use repeated calls to one model, not separate skills or agents.
- The [Anthropic postmortem](https://www.anthropic.com/engineering/april-23-postmortem) shows one shared instruction can regress models; one incident does not quantify our risk. OMP's `omp://skills.md` documents hidden autoload and `skill://` resolution; runtime facts do not establish decision quality.
